Documentation · Security

Security

Warden is intentionally powerful, so security is defined by server-side capabilities, filesystem validation and OS authority—not by hidden controls.

Implemented controls

  • server-side multi-user accounts, identities, reusable roles and capability checks;
  • 12-hour HttpOnly, SameSite=Strict browser sessions and per-session CSRF tokens;
  • seven-character minimum account passwords, rate limiting, optional TOTP and recovery codes;
  • AES-GCM encrypted recoverable secrets;
  • same-origin authentication and CSRF checks for terminal WebSockets;
  • trusted forwarded headers only when the direct reverse-proxy peer is loopback;
  • filesystem confinement with symlink resolution and atomic editor writes;
  • typed administrative actions and structured SQLite audit events;
  • account ownership for conversations, terminal metadata and acknowledgements.

Remote deployment

Keep Warden on loopback behind Caddy or nginx, enable WARDEN_TRUST_PROXY=true only for a local proxy you control, and use HTTPS. Warden uses trusted X-Forwarded-Proto when deciding whether cookies must be Secure; a remote client cannot become trusted merely by sending forwarded headers.

Authority

Application accounts are not OS sandboxes.

Terminal and Agent processes run with the operating-system authority of the user that launched Warden. Grant terminal.open and agent.run accordingly. For OS-level isolation, run separate Warden instances under separate system users or stronger containment.

Operational data

warden.db, JSON compatibility files, encrypted secrets and master.key all live inside the private configuration directory. Preserve owner-only permissions and back up the directory as a unit.
