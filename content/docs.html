Documentation

Warden

Warden is a security-conscious web console for Linux servers. Nift builds the frontend; a dependency-light Go service owns authentication, monitoring, filesystem operations, structured administration and the interactive PTY terminal.

Current status

Development build.

The current v1 slice is intended for local/private dogfooding. Do not expose it directly to the public Internet yet. The application has meaningful security controls, but the planned adversarial security campaign, proxy-trust hardening, session-management work and broader deployment testing are not complete.

Warden is deliberately more than a read-only dashboard. An authenticated user can edit files, operate a terminal and invoke structured administrative actions. That makes the authority boundary important: Warden can only be as constrained as the operating-system identity and configuration under which it runs.

Build and run

Build the Nift frontend

nift build

The generated frontend lives in public/. Nift remains the build-time composition/dependency layer; runtime behavior stays ordinary browser JavaScript talking to the Go API.

Build the Go service

go build -o warden ./cmd/warden

Create a password hash

./warden hash-password 'choose-a-strong-password'

Warden does not store a default cleartext password. hash-password emits a PBKDF2-HMAC-SHA256 hash using a random salt and 310,000 iterations.

Start locally

export WARDEN_PASSWORD_HASH='pbkdf2-sha256$...'
./warden

The default listener is 127.0.0.1:8080. Open that address in a browser. Loopback development permits a non-Secure session cookie so local HTTP works; non-loopback listeners default to Secure cookies.

Security model

Warden's current controls are implemented in the server, not only in the UI:

  • server-side 12-hour sessions with an HttpOnly, SameSite=Strict cookie;
  • per-session CSRF tokens required for state-changing API requests;
  • login rate limiting per direct client address;
  • WebSocket terminal upgrades require authentication, CSRF and matching Origin/Host;
  • restrictive CSP, frame, referrer and content-type response headers;
  • filesystem paths are resolved against one configured file-management root, including symlink resolution;
  • editor writes use temporary-file + fsync + atomic rename and preserve existing permission bits;
  • privileged activity is appended to warden-audit.log, created with mode 0600.
The terminal is a separate authority boundary.

--root / WARDEN_FILE_ROOT confines Explorer and Editor file APIs. It does not sandbox the PTY. The terminal starts in the configured user's home directory and executes with the Warden process user's normal OS authority.

WARDEN_TRUST_PROXY exists in configuration but the current client-address helper still uses the direct peer address. Do not assume generic forwarded headers are trusted client identity. A precise trusted-proxy model remains future hardening work.

Monitor

The Overview page reads Linux system information through the Go backend and renders it as structured cards and browser-side graphs. The current surface includes CPU usage/load, memory, root-filesystem storage, hostname, uptime, process count and runtime information.

The monitor is intended to answer common “what is this machine doing?” questions quickly without turning the page into a terminal transcript. It is a convenience/observability surface, not a replacement for a full metrics stack such as Prometheus.

Explorer

Explorer starts in the server user's home directory by default while allowing navigation up to the configured file root. It is intentionally separate from the Editor so bulk file management can have a file-manager interaction model.

  • size and modified-time columns;
  • multi-select with upload, create, rename, copy, move and delete operations;
  • download of files and archive download for selections;
  • ZIP compression and extraction with path-confinement checks;
  • inline image, video and audio preview;
  • home jump plus root-aware breadcrumbs.

Set --root /some/subtree or WARDEN_FILE_ROOT when you intentionally want a narrower Explorer/Editor view. Warden resolves candidate paths and symlinks inside that root rather than trusting string prefixes.

Workspace editor

The Editor is workspace-oriented rather than a textarea bolted onto the Explorer. Its own tree can open directories in-place, keep multiple files in tabs and search across the active workspace.

  • syntax-highlighted text editing with word wrap;
  • multiple open tabs and VS Code-style workspace tree;
  • native undo/redo behavior including Ctrl+Z;
  • workspace search and replace, case-sensitive mode and regular expressions;
  • atomic saves with permission preservation;
  • download of the currently open file.

Search/replace is intentionally a filesystem operation performed through the authenticated backend, so its confinement follows the same configured root as other file APIs.

Interactive terminal

The Terminal is a real Linux PTY exposed over an authenticated WebSocket. Common ANSI/SGR colours are preserved in the browser. Terminal access is therefore not a cosmetic dashboard feature—it gives the session the practical authority of the account running Warden.

Design roles around the PTY, not around the buttons.

Future viewer/operator/admin roles must treat terminal entitlement as an explicit capability. Hiding a dangerous structured action while leaving unrestricted terminal access would not create a meaningful security boundary.

Structured system administration

The System menu presents typed state and explicit actions rather than dumping raw command output into textareas. Availability depends on the host and Warden process permissions.

Certificates

Reads common TLS certificate locations, including Let's Encrypt paths, and reports subject, issuer, names and expiry. Managed certificate actions are constrained to validated inputs.

Cron

Displays system cron files and the current user's crontab as structured schedules/commands. User-crontab changes validate schedule/action input before invoking the system tool.

Docker

Talks directly to the local Docker Unix socket for version/container state and supports bounded container actions when the socket is available.

Fail2ban

Lists jails and status through fail2ban-client, with validated jail/IP inputs for supported actions.

Firewall

Reads UFW status/rules and applies validated allow/delete operations rather than accepting arbitrary shell fragments.

Services

Lists systemd services at system or user scope and exposes structured service actions. Unit names and action values are validated.

SSH

Surfaces selected sshd_config settings and service state, with bounded configuration actions.

Users

Reads account information from /etc/passwd, distinguishes system versus login users, and validates usernames/actions for supported administration.

Deployment boundary

For current dogfooding, prefer loopback access, a private network or a private tunnel. If you place Warden behind HTTPS, set Secure cookies appropriately and keep the reverse proxy's origin/host behavior compatible with the WebSocket same-origin check.

Before recommending Internet-facing deployment, Warden still needs the planned adversarial security corpus, explicit trusted-proxy semantics, stronger session revocation/management, optional 2FA, audit rotation/structure, deployment hardening and broader hostile-input testing.

Current rule of thumb.

If you would not give an authenticated visitor shell access as the Warden process user, do not give them Warden access either.
