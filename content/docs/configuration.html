Documentation · Configuration

Configuration

Warden keeps durable instance configuration in small, versioned JSON files that can be managed through the browser or edited directly on disk.

Configuration directory

By default Warden uses ~/.config/warden/, or $XDG_CONFIG_HOME/warden/ when XDG configuration is set. Override the location with --config or WARDEN_CONFIG_DIR.

~/.config/warden/
  config.json
  environment.json
  authentication.json
  ai.json
  users.json
  roles.json
  secrets.json
  ai-usage.json

Warden creates these files with owner-only permissions. JSON writes are staged and atomically replaced, and browser writes retain a .bak copy of the previous valid file.

Once config.json exists it is the durable source of truth; bootstrap flags do not silently overwrite it on later starts.

Browser-managed environment

System → Warden includes a persistent environment editor. Variables saved there are written to environment.json and merged into every new terminal session. Existing PTYs keep the environment they were launched with.

This avoids requiring users to edit .bashrc or export variables after every login. Each Warden account can manage its own persistent overrides from Security → Your environment; administrators can also edit them centrally from Access. Account values override instance-wide values.

Direct JSON edits and reload

You can edit Warden JSON through Explorer/Editor or directly on the filesystem. Use Reload configuration in System → Warden afterwards. Warden reads and validates instance, environment, authentication, AI, account/role and encrypted-secret stores first; only after the complete candidate is valid are the in-memory snapshots replaced. An invalid file therefore cannot partially change the running authorization/configuration state.

Fields that affect the listener, filesystem root, frontend directory or cookie/proxy policy are reported as requiring a Warden restart rather than being half-switched under active sessions.

Authoritative frontend files live under content/ and templates/; public/ is generated output.

Backup, reinstall and reset

System → Warden exposes the current executable/install style and can export or import a portable configuration bundle containing instance settings, accounts, password hashes, roles, environment, authentication settings and AI provider defaults. Import validates the whole bundle, requires at least one enabled administrator and revokes existing browser sessions after replacement. Encrypted backups are decrypted only in memory and their secrets are re-encrypted using the destination instance’s own master key. The ordinary export intentionally excludes encrypted secrets. Export + secrets creates a password-encrypted portable backup that includes TOTP seeds, Google client secrets and AI credentials without copying the machine-local master.key.

Reset authentication requires the acting administrator to re-enter their Warden password, removes all Warden accounts and sessions, and returns the instance to browser-first setup. Reset Warden state also requires password confirmation and returns Warden-owned configuration, roles, environment, AI settings, secrets and usage data to first-run defaults. Neither operation deletes repositories, projects or other workspace files; audit history is retained.

Package-managed installations should continue to use their package manager for updates/uninstall. The persistent configuration directory is deliberately independent of the executable so replacing or reinstalling Warden does not silently erase account state.
