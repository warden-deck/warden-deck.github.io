Battle Tested

Warden's hardening campaign publishes what was attacked, what passed and what remains risky. This page is an evidence ledger, not a security slogan.

Current status

Campaign planned, not yet completed.

The 18-checkpoint programme has been defined against Warden's current authentication, authorization, filesystem, terminal, agent, administration and persistence boundaries. Existing focused tests are useful baseline evidence, but they are not presented as completion of the adversarial campaign.

Warden remains a development build. Keep it bound to loopback behind a trusted HTTPS reverse proxy, run it with deliberately limited operating-system authority, grant terminal and agent capabilities sparingly, and maintain tested backups.

What counts as evidence

  • a named threat and invariant;
  • a reproducible adversarial test or operational drill;
  • a regression test for every repaired finding;
  • focused tests plus the full Go, race, vet, frontend and Nift gates;
  • exact commits, environment and retained limitations;
  • public documentation updated in the same checkpoint.

A green test run proves only the cases and environment it exercised. Warden will not translate one fuzz run or deployment drill into a universal "secure" claim.

Already implemented, awaiting campaign validation

Warden already includes server-side sessions, per-session CSRF tokens, password throttling, optional TOTP, Google OAuth with PKCE, capability-bearing accounts, encrypted secret storage, trusted-proxy restrictions, filesystem path resolution, atomic saves, authenticated terminal WebSockets, SQLite state and audit events. The campaign will test these as interacting systems and repair any gap it finds.

Known authority limit

Warden accounts are not operating-system sandboxes.

Terminal and coding-agent subprocesses inherit the authority of the operating-system user running Warden. Separate OS users or stronger containment remain necessary when users require OS-level isolation.

How this page will evolve

Every completed checkpoint will replace its planned status with the date, exact evidence, relevant commits, repaired findings and retained limitations. Related feature pages will be updated at the same time so this ledger never becomes the only accurate page on the site.
