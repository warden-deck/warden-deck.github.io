Security

Warden is intentionally powerful, so security is defined by server-side boundaries and operating-system authority rather than by which controls happen to be visible.

Implemented controls

  • persistent server-side 12-hour sessions with HttpOnly, SameSite=Strict cookies;
  • per-session CSRF tokens for state-changing HTTP requests;
  • login rate limiting by direct client address;
  • optional per-password-identity TOTP with one-time recovery codes;
  • AES-GCM encrypted storage for recoverable secrets;
  • same-origin checks plus authentication/CSRF for terminal WebSockets;
  • restrictive CSP, frame, referrer and content-type headers;
  • filesystem confinement with symlink resolution;
  • atomic editor writes and permission preservation;
  • structured administrative actions rather than arbitrary command strings;
  • privileged activity appended to a mode-0600 audit log.

Current deployment position

Private dogfooding, not a blanket Internet recommendation.

The planned adversarial security corpus, explicit trusted-proxy semantics, broader session management, optional stronger authentication and deployment hardening are not complete.

Prefer loopback, a trusted private network or a private tunnel. If Warden sits behind HTTPS, configure Secure cookies and preserve the WebSocket origin/host assumptions.

Terminal authority

The PTY is the largest capability boundary. If an authenticated visitor should not receive a shell as the Warden OS user, they should not receive terminal-enabled Warden access either.
