Documentation · Durability

SQLite and durable state

Warden uses a protected SQLite database for conversations, terminal history, alerts, website revisions, operation jobs and normalized application state.

Database foundation

warden.db lives in the private configuration directory with owner-only permissions. Numbered migrations run transactionally at startup; foreign keys, WAL journaling, full synchronous writes and a busy timeout are enabled. Warden refuses schemas newer than the running binary.

Durable operational objects

  • account-owned agent conversations, transcript events and individual agent runs;
  • account-owned terminal tabs and bounded server-side scrollback;
  • alert rules, evaluation state, firing/resolved incidents, events and acknowledgements;
  • website definitions, domains, immutable revisions and asynchronous operation jobs;
  • normalized accounts, identities, roles/capabilities, browser sessions and AI usage totals;
  • structured audit events, including an idempotent import of the earlier audit log.

Compatibility migration

Existing JSON account, role, session and AI-usage stores are imported into normalized SQLite tables. Warden retains a compatibility mirror so current backup/export workflows continue to operate during the transition. Legacy browser conversations are imported only when an account has no server-side conversations.

Backup boundary

The binary is self-contained; instance data is not.

Back up the entire configuration directory, including warden.db, JSON compatibility files, master.key and encrypted secrets. Copying only the executable does not move the instance.
