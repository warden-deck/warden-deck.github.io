Audit and sessions

Multi-user Warden records which account and login identity performed authenticated administrative and workspace actions, and gives users control over their active browser sessions.

Identity-aware audit log

Warden stores audit.log inside the private instance configuration directory. Authenticated events record the Warden account ID, the specific login identity ID and the client address alongside the action. This matters when several people deliberately share one Warden account through different identities.

Users with the audit.read capability can inspect the recent audit tail from System → Audit. The capability is independent of other system-administration permissions.

Session control

System → Security lists the current account's active browser sessions with their client address, user agent and expiry. A user can revoke an individual session. Administrators can revoke every session for an account from System → Access, which is useful after credential changes or when removing access.

Account and identity removal

Administrators can remove individual login identities or delete a Warden account. Warden refuses to remove the final login-capable identity from an account and refuses to delete or disable the final enabled administrator. Removing an identity revokes sessions established through it and removes its TOTP secret where applicable.

Workspace files are external data.

Deleting a Warden account removes Warden identity/session state and account-specific settings. It does not delete repositories, home directories or workspace files.
